# 管理员角色方案

## 1. 背景与目标

当前所有「管理端」接口只要求登录，任何注册用户都能调用商品/分类/品牌的增删改、秒杀活动创建等敏感操作。本期目标：引入管理员角色，让后台管理接口只对管理员开放，为 `frontend/admin` 提供安全前提。

## 2. 现状分析

梳理现有鉴权链路，确定改动点：

| 环节 | 现状 | 缺口 |
|---|---|---|
| JWT 签发（user） | `subject` 只放 userId，无角色信息 | 需在 claim 中携带角色 |
| 用户数据 | `t_user` 无角色字段，只有 `status` | 需新增 `role` 字段 |
| 网关校验 | 解析 token → 透传 `X-User-Id`，无角色 | 需解析并校验角色 |
| 下游服务 | 从 `X-User-Id` 取身份，无角色概念 | 无需改动（信任网关） |

## 3. 数据模型

`t_user` 新增角色字段：

```sql
ALTER TABLE t_user
    ADD COLUMN role TINYINT NOT NULL DEFAULT 0 COMMENT '角色:0普通用户 1管理员';
```

对应枚举：

```java
public enum UserRole {
    USER(0, "普通用户"),
    ADMIN(1, "管理员");
}
```

## 4. JWT 扩展

签发时携带角色：

```java
String token = Jwts.builder()
        .subject(String.valueOf(user.getId()))
        .claim("role", user.getRole())   // 新增
        .issuedAt(now)
        .expiration(expiry)
        .signWith(secretKey)
        .compact();
```

网关解析时一并取出角色，作为 `X-User-Role` 透传。

## 5. 网关角色校验

### 5.1 配置扩展

在 `GatewayProperties` 增加 `adminPaths` 列表，与 `whitelist` 并列，格式同为「方法:路径」，表示「该路径需要管理员角色」。

### 5.2 过滤器逻辑

```text
1. 命中白名单 → 放行
2. 校验 token → 解析 userId + role
3. 覆盖/清除客户端传入的 X-User-Id、X-User-Role 头
4. 透传 X-User-Id、X-User-Role
5. 命中 adminPaths 且 role != ADMIN → 返回 403
6. 放行
```

> 关键安全点：网关必须**覆盖**客户端伪造的 `X-User-Id` / `X-User-Role` 头，避免绕过。

### 5.3 管理端路径清单（首批）

| 方法:路径 | 说明 |
|---|---|
| POST:/api/product | 新增商品 |
| PUT:/api/product/* | 修改商品 / 上下架 |
| DELETE:/api/product/* | 删除商品 |
| POST:/api/product/category | 新增分类 |
| PUT:/api/product/category/* | 修改分类 |
| DELETE:/api/product/category/* | 删除分类 |
| POST:/api/product/brand | 新增品牌 |
| PUT:/api/product/brand/* | 修改品牌 |
| DELETE:/api/product/brand/* | 删除品牌 |
| POST:/api/promotion/seckill/activity | 创建秒杀活动 |
| POST:/api/promotion/seckill/activity/*/warmup | 预热库存 |

> 后续新增「订单管理」「用户管理」管理员接口时，同步把路径加进 `adminPaths`。

## 6. 关键决策：在网关统一校验

采用「网关统一校验角色」而非「各服务分别校验」：

- 优点：改动集中在 `gateway` + `user`，下游服务零改动；规则集中、易维护。
- 代价：网关需维护 `adminPaths` 清单，与后端新增后台接口保持同步。
- 适用前提：下游服务不直接暴露公网，只经网关访问，因此可信任 `X-User-Role` 头。

> 若未来要求服务级细粒度权限（如操作级授权），再下沉到各服务用注解/拦截器做二次校验。

## 7. 实施步骤

1. `t_user` 执行 `ALTER TABLE` 加 `role` 字段，并初始化一个管理员账号（`UPDATE t_user SET role=1 WHERE username='admin'`）。
2. `user`：新增 `UserRole` 枚举，`User` 实体加 `role` 字段，`JwtUtil.generateToken` 增加 `role` claim。
3. `gateway`：`JwtUtil` 解析 `role`，`GatewayProperties` 增加 `adminPaths`，`AuthGlobalFilter` 增加角色校验与 `X-User-Role` 透传，`application.yml` 配置 `adminPaths`。
4. 返回 403 的统一响应：`{"code":403,"message":"无权限访问"}`。
5. 联调验证：普通用户访问管理端路径返回 403，管理员正常通过。

## 8. 影响范围与风险

- 影响：`user`（登录签发）、`gateway`（鉴权过滤）、`t_user` 表。
- 不影响：下游各服务的业务逻辑；用户端浏览接口仍公开。
- 风险：老 token 不含 role，升级后需重新登录；`adminPaths` 漏配会导致对应接口无角色保护。

## 9. 验收标准

- 普通用户访问管理端接口返回 `403`，访问用户端接口正常。
- 管理员访问管理端接口正常。
- 客户端伪造 `X-User-Role: 1` 无法绕过（网关覆盖该头）。
- token 不含 role 时，访问管理端接口返回 `403`。
