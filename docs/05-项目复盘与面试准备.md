# 项目复盘与面试准备

> 本文档用于复习「次元匣社 / DIMBOX」项目所学知识，并支撑简历撰写与面试表述。
> 阅读方式：先看「项目概览」建立全局，再逐个吃透「技术亮点」，最后过一遍「踩坑记录」。

## 1. 项目概览

**一句话介绍**：一个前后端分离的潮玩商城，后端采用 Spring Cloud Alibaba 微服务架构，覆盖「注册登录 → 浏览商品 → 下单扣库存 → 支付 → 秒杀抢购」完整交易链路，并实现了防超卖、幂等、异步削峰等高并发场景下的关键技术。

**技术栈**：

| 层 | 技术 |
|---|---|
| 后端 | JDK 17、Spring Boot 3.2.4、Spring Cloud 2023.0.1、Spring Cloud Alibaba 2023.0.1.0 |
| 持久层 | MyBatis-Plus 3.5.7、MySQL 8 |
| 中间件 | Nacos（注册/配置）、Redis（缓存/库存预扣）、RabbitMQ（削峰/异步） |
| 前端 | Vue 3 + Vite + Element Plus + Pinia + Vue Router + Axios |
| 工程 | Maven 多模块、Git 分支工作流、Docker（虚拟机模拟环境） |

**服务划分与职责**：

| 服务 | 端口 | 职责 |
|---|---|---|
| gateway | 8080 | 统一入口、路由转发、JWT 鉴权、用户身份透传 |
| user | 8081 | 注册登录、JWT 签发、资料、地址 |
| product | 8082 | 分类、品牌、商品（SPU/SKU）、库存 |
| order | 8083 | 下单、订单状态机、取消回补库存 |
| payment | 8085 | 支付单、mock 支付、支付回调 |
| promotion | 8084 | 秒杀活动、Redis 预扣、MQ 落库、限流 |
| common | - | 统一返回、错误码、异常、分页 |

## 2. 技术亮点

每个亮点按「背景 → 方案 → 面试怎么讲 → 可能被追问」组织。

### 2.1 秒杀防超卖（核心亮点）

**背景**：秒杀场景大量请求同时抢同一商品，直接查库再扣减会超卖，且数据库行锁会成为瓶颈。

**方案**：分四层防护，逐层递进：

1. 数据库层：原子条件扣减，`UPDATE ... SET stock = stock - n WHERE id = ? AND stock >= n`，用受影响行数判断，是正确性的最后防线。
2. 缓存层：库存预热到 Redis，用 Lua 脚本原子完成「限购检查 + 库存校验 + 扣减 + 记录用户」，Redis 单线程保证原子。
3. 削峰层：Redis 扣减成功后发 RabbitMQ 消息，异步落库完成最终扣减，接口立即返回不等落库。
4. 流量层：Sentinel 对抢购接口做 QPS 限流。

**面试怎么讲**：突出「为什么分层」——DB 原子扣减保证正确但扛不住并发，Redis Lua 扛并发但内存数据要最终落库，MQ 削峰避免落库阻塞用户，Sentinel 挡恶意流量。强调这是一个「从正确性到性能」的完整思考。

**追问点**：

- Redis 和 DB 库存不一致怎么办？→ 最终一致，MQ 重试 + 死信兜底。
- 消息重复消费怎么办？→ 幂等（见 2.2）。
- 为什么用 Lua 而不是多条 Redis 命令？→ 多条命令之间会被穿插，Lua 在服务端单线程原子执行。

### 2.2 幂等设计

**背景**：重复提交、MQ 重复投递、支付回调重复，都会导致重复扣库存、重复建单。

**方案**（三个层次的幂等）：

- 下单幂等：客户端传 `requestId`，订单表加唯一索引，重复请求返回原订单，不重复扣库存。
- 秒杀限购幂等：Redis Set 集合记录已抢用户，`sismember` 判断，天然幂等。
- 消费幂等：`t_seckill_order` 用 `(activity_id, user_id)` 唯一索引，重复消息直接忽略。

**面试怎么讲**：强调「唯一索引是幂等的最后防线」，因为数据库唯一约束在并发下依然可靠，业务层的先查后插有竞态窗口。

### 2.3 分布式一致性（最终一致）

**背景**：下单跨 order（建单）和 product（扣库存）两个服务；支付跨 payment（支付单）和 order（状态推进）。

**方案**：P0 不引入 Seata，用「先扣减、失败回补」+「回调可重试」的最终一致思路：

- 下单：先 Feign 原子扣库存，再本地事务建单；建单失败回补库存。
- 取消：先回补库存再改状态，方向保证「已取消 → 库存已回补」。
- 支付：先推进订单状态（幂等），再更新支付单，回调可安全重试。

**面试怎么讲**：主动说明「没有用 Seata，而是选了更轻的最终一致」，并讲清权衡——Seata 重、引入复杂，P0 用补偿 + 幂等 + 重试够用。这体现你理解「一致性」不止一种解法。

### 2.4 雪花 ID 精度丢失问题

**背景**：雪花 ID 是 19 位 Long，超过 JS `Number.MAX_SAFE_INTEGER`（16 位），前端 JSON 解析会丢精度。

**方案**：后端全局把 `Long` 序列化为字符串（Jackson 自定义序列化器），前端全程用字符串处理 ID。

**面试怎么讲**：这是真实踩坑，能体现「遇到问题定位到根本原因」的能力。定位链路：前端拿到的 ID 对不上 → 发现是 JS 精度 → 后端序列化层统一修复，而不是前端一个个改。

### 2.5 网关统一鉴权与身份透传

**方案**：gateway 全局过滤器校验 JWT，白名单放行；校验通过后把 `userId` 放入 `X-User-Id` 请求头透传给下游，下游不再重复解析 token。

**面试怎么讲**：强调「鉴权收敛在网关」，下游服务无状态、职责单一，符合微服务设计。

### 2.6 MQ 异步削峰

**方案**：秒杀抢购成功后，立即返回「抢购成功」，把落库动作交给 RabbitMQ 消费者异步完成。

**面试怎么讲**：突出「接口响应快」和「DB 压力平缓」两个收益，以及消息队列带来的幂等、重试、最终一致等配套问题。

### 2.7 统一返回与异常体系

**方案**：`Result<T>` 统一响应结构，`code` 与 HTTP 状态码一致；业务异常抛 `BizException`，由全局 `@RestControllerAdvice` 统一转换；错误码枚举管理。

**面试怎么讲**：说明这是「接口契约一致性」的工程实践，避免各服务各写一套返回格式。

### 2.8 可靠消息消费：手动 ack + 死信队列 + 消费幂等

**背景**：秒杀抢购成功后发 MQ 异步落库，但存在两个问题——消费失败会无限 requeue 堵死队列，重复消费会重复扣库存。

**方案**：

- 手动 ack：消费成功 `basicAck`，失败 `basicNack(requeue=false)`，坏消息不回队列无限循环。
- 死信队列：业务队列绑定死信交换机，nack 的消息进死信兜底，可人工重放。
- 消费幂等 + 状态机：`t_seckill_order` 用 `(activity_id, user_id)` 唯一索引保证「同一用户同一活动只插一条」，`status` 字段区分「0 待扣库存 / 1 已扣库存」。扣库存失败保留 `status=0`，重投时按状态补扣，不依赖删除。

**面试怎么讲**：强调「可靠消息投递的三板斧」——确认机制（ack 不丢）、失败隔离（死信不堵）、幂等（唯一索引不重），并讲清三者之间的配合关系。

**追问点**：为什么 `requeue=false`？状态机和删记录补偿有什么区别？（见 3.8）

## 3. 踩坑记录

每个坑按「现象 → 原因 → 解决 → 启示」记录，面试被问「项目里遇到什么难点」时，这些都是真实素材。

### 3.1 IDEA 编码导致 YAML 启动失败

- 现象：`application.yml` 里有中文注释，启动报 `MalformedInputException: Input length = 1`。
- 原因：IDEA 未给 resources 目录设 UTF-8，编译时把 yml 转成了 GBK，Spring Boot 用 UTF-8 读取失败。
- 解决：统一 IDEA 全局编码为 UTF-8，并去掉 yml 里的中文注释。
- 启示：源码没问题时，先怀疑「编译产物」和「IDE 编码设置」。

### 3.2 Maven 父工程解析失败

- 现象：子模块 pom 报 `Project 'com.dimbox:backend' not found`。
- 原因：子模块 `<parent>` 缺 `<relativePath>../pom.xml</relativePath>`，父工程又未装进本地仓库。
- 解决：统一补上 relativePath。
- 启示：Maven 多模块工程，子模块的 parent 要显式声明相对路径。

### 3.3 网关 lb:// 转发找不到负载均衡器

- 现象：网关用 `lb://dimbox-user` 转发报错。
- 原因：`spring-cloud-starter-gateway` 默认不带 LoadBalancer。
- 解决：额外引入 `spring-cloud-starter-loadbalancer`。
- 启示：Spring Cloud 版本间的 starter 边界要清楚，`lb://` 依赖 LoadBalancer。

### 3.4 Lua 脚本括号抄错

- 现象：抢购接口返回 500。
- 原因：Lua 里 `tonumber(redis.call('get', KEYS[1]) or '0')` 抄成了 `tonumber(redis.call('get', KEYS[1] or '0')`，少了右括号。
- 解决：改正括号层级。
- 启示：Lua 嵌套函数调用括号要格外小心，报 500 时先看日志堆栈再猜。

### 3.5 Mockito 严格模式报 UnnecessaryStubbing

- 现象：单测报 `UnnecessaryStubbingException`。
- 原因：把 stub 放进了 `setUp`，但某些用例用不到它。
- 解决：每个测试只 stub 自己真正用到的依赖。
- 启示：Mockito 严格模式会检查无用 stub，这是良好测试习惯的约束。

### 3.6 接口 404 因路径单复数不一致

- 现象：访问 `/record` 返回 404。
- 原因：Controller 写的是 `/records`，差一个字母。
- 解决：统一为文档约定的单数路径。
- 启示：路径是精确匹配，排查 404 先逐字对比 Controller 映射和请求 URL。

### 3.7 换 token 仍「已抢购」的排查

- 现象：换 token、换活动都返回「已抢购」。
- 原因：两个 token 实际解析出同一个 `userId`，限购是按 userId 判定的。
- 解决：用 `/user/me` 确认每个 token 的真实身份。
- 启示：排查「按用户隔离」的问题，先确认用户身份是否真的不同。

### 3.8 幂等闸与扣库存的时序矛盾（两次修复，最终方案为状态机）

- 现象：MQ 消费者「先 insert 后扣库存」，扣库存失败重试时 insert 撞唯一索引被吞，导致 DB 库存漏扣，Redis、秒杀记录、DB 库存三处不一致。
- 原因：insert 是幂等闸，一旦成功就永久占用唯一索引；后续重试无论扣库存是否成功，都会先撞索引被跳过。
- 第一次修复（删记录补偿）：扣库存失败时删除刚 insert 的记录再重试。
- 第二次发现：`deleteById` 是逻辑删除（`@TableLogic`），只把 `deleted` 置 1，不释放唯一索引，死信重投时 insert 仍撞索引被吞，删记录补偿失效。
- 最终方案（状态机）：不删除记录，改用 `status` 区分「0 待扣库存 / 1 已扣库存」。消费时按状态判断——1 表示已扣（ack 跳过），0 表示未扣（继续补扣）。唯一索引退化为「去重闸」，状态字段才是真正的「幂等判断」。
- 启示：幂等设计和最终一致性要一起想。逻辑删除与唯一索引会互相牵制，「删了重插」的补偿思路在逻辑删除下走不通，正确方向是记录状态机。

```text
潮玩商城（前后端分离微服务）

- 设计秒杀模块：Redis 预热 + Lua 原子扣减 + RabbitMQ 异步削峰 + Sentinel 限流，压测验证 50 并发抢 10 库存未超卖。
```
