# payment 模块需求文档

## 1. 背景与目标

`payment` 是交易链路的最后一块。本期目标：为订单生成支付单、完成支付（mock 渠道）、处理支付回调，并把订单状态从「待支付」推进到「已支付」，从而打通「下单 → 支付 → 状态流转」的完整闭环。

## 2. 用户与场景

- 已登录用户：对「待支付」订单发起支付、查询支付状态。
- 支付渠道：真实渠道（支付宝/微信）后续接入，本期用 mock 支付模拟「支付成功」回调。

## 3. 功能范围

### 本期 P0

| 编号 | 功能 | 说明 |
|---|---|---|
| PAY-01 | 创建支付单 | 为待支付订单生成支付单，返回支付单号 |
| PAY-02 | 发起支付 | mock 渠道返回模拟支付结果 |
| PAY-03 | 支付回调 | 幂等处理，更新支付单并通知订单已支付 |
| PAY-04 | 查询支付单 | 查询支付单状态与金额 |

### 后续（不在本期）

- 对接支付宝/微信沙箱、退款、支付对账、超时关闭支付单。

## 4. 功能详述

### PAY-01 创建支付单

- 入参：`orderNo`。
- 校验：订单存在、属于当前用户、状态为「待支付」。
- 同一订单若已有待支付支付单，直接返回原支付单（幂等）。
- 金额以订单金额为准，不在前端传递。

### PAY-02 / PAY-03 支付与回调

- P0 用 mock 渠道：调用支付接口即视为「支付成功」，内部走与真实回调一致的逻辑。
- 回调幂等：同一支付单重复回调，只处理一次，状态只前进不后退。
- 回调成功后：支付单置为「已支付」，并通知 order 把订单置为「已支付」。

### PAY-04 查询支付单

- 返回支付单号、订单号、金额、状态、支付时间。
- 按用户隔离。

## 5. 非功能需求

- 幂等：创建支付单与支付回调均幂等。
- 一致性：支付成功与订单状态推进用「先改支付单、再通知订单 + 失败重试」保证最终一致。
- 安全：金额以服务端为准，支付单按用户隔离。

## 6. 验收标准

- 对待支付订单能创建支付单，重复创建返回同一支付单。
- mock 支付成功后，支付单与订单状态都变为「已支付」。
- 重复回调不产生副作用，状态不倒退。
- 非本人支付单无法查询或操作。
